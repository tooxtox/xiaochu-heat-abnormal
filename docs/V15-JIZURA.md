# V15：JIZURA 字面歌词导演层

这一版把歌词层从"引擎自动规划 + 随机挑选版式"改成**逐行语义导演**。
引擎（JIZURA 字面，MIT License，© 2026 hakoniwa）只负责把字画出来；
每一行唱什么、怎么出现、什么颜色、用什么底板，都由 `data/jizura_direction.json` 决定。

歌词文本本身不入库：`data/lyrics.json` 属于权利方，仓库只发布方向与标记。

## 一、方向表是怎么来的

`tools/build_jizura_direction.py` 从四张表生成方向表：

| 来源 | 内容 |
| --- | --- |
| `data/lyrics.json` | 126 行日中歌词与行级时间 |
| `data/shots.json` | 镜头表（模式 / 起止） |
| `data/jizura_planes.json` | 转场吞字审计结果（`tools/jizura_plane_audit.mjs`） |
| `data/jizura_variants.json` | 墨色极性的实测择优（`tools/jizura_variant_probe.mjs`） |
| `data/jizura_lyric_marks.json` | 强调词与断句标注（带歌词原文，只在本地） |

强调词（`*词*`）与断句（`/`）这两张表里带歌词原文，属权利方内容，因此放在
`data/jizura_lyric_marks.json` 而不是写死在生成器里，两者都不入库。
缺少该文件时导演表仍能生成，只是不带强调与分句——版式、配色与镜头不受影响。

方向表本身是**可读、可复查、可重跑**的：每行写明
`move`（语义动作）、`family`/`plan`（配色世界与极性）、`layout`、
`enter`/`exit`/`hold`、`decor`/`treat`/`cam`、`cuts`/`cutTech`、
`emphasis`/`break`/`kime`（交给引擎解析器的标记），以及一句中文 `note` 说明
"为什么这一行是这个效果"。共 96 个语义动作、12 个计划、126 行。

语义动作按歌词的意思归类，例如：

- `erase-1`…`erase-8`：一句"消去しても"拆成八次删除，每次版式与破坏程度递进；
- `near-1`…`near-8`：一句"すぐそこまで"逼近八次，字越来越近、越来越碎；
- `star-1`…`star-8`：黑星段，字绕着星走，最后碎成星轨；
- `whisper-1`…`whisper-8`：低语段，小字、模糊、最终化成雾；
- `turn-1`…`turn-7`：背向段，镜像翻转，字转过身去。

## 二、配色世界服从影片调色板

影片自己的调色板（`src/palette.mjs`）：薄荷 `#9DE4C2`、橙 `#ED8B50`、
红 `#D93B4A`、粉 `#E9ACC8`、纸白 `#E9EDE5`、黑 `#090C13`。
JIZURA 自带的糖果粉与薄荷绿铺成大色块时会和影片的暖调打架，所以全部换掉。

每个配色家族有**两种墨色极性**：

| 极性 | 底板 / 字色 | 用在 |
| --- | --- | --- |
| A | 暗底板 + 浅字（黑底纸白字） | 暗画面 |
| B | 纸白底板 + 深墨字（纸白底黑字） | 亮画面（燃烧段的红天空、白色记忆房间） |

（「light」家族是反过来的：它本身就属于亮场景，默认就是 B 极性的纸底深墨。）

**用哪一种不靠手写名单，靠实测。** `tools/jizura_variant_probe.mjs` 把同一句话的
两种极性都渲染出来，量它们在真实画面上的 WCAG 对比度，择优写进
`data/jizura_variants.json`。差值小于 0.6 就保留家族默认极性，避免为了
一点点数字改动破坏美术方向。

**但探针量的是"这一行整体贡献了多少对比度"，不是"字本身读不读得出来"。**
遇到带自己底板的版式（价签、名牌、票根）时，探针量到的是那块底板，
不是底板上的字。这种行要靠 A/B 静帧复核。

实际翻车的只有一行：**L116「腐りきった三日月が笑っている」**（224.04–225.67 秒，
`arcTop` 弧顶版式，落在纸白的记忆房间里）。探针判"深底浅字"更好（3.13 vs 2.14），
但弧顶版式在纸白背景上画的是浅墨描边字——A/B 静帧上几乎完全看不见；
换成纸底深墨后字立刻读得出来。这行因此在 `data/jizura_variants.json` 里
人工改判为 `darkAlt`，并写明理由。其余十行 weak / missing 全部经 A/B 复核，
结论是维持原极性。

> 引擎里 `sc.ink`（版式元素——底板、框、色带用的颜色）不随 `colors` 变化，
> 所以每种极性配一个 `sc.ink` 方向一致的风格：暗底配浅墨风格，纸底配深墨风格。
> 风格还决定字体与纸纹，所以这不只是换个颜色。

## 三、字在人后 vs 字在人前

「字在人后」不是手写清单，而是按镜头覆盖算出来：

- 这一行主要落在眼部／手部插入镜头上（画面主体就是那只眼睛或那只手）→ **必须前层**；
- 主要镜头是 wide / abstract / world（人物不在画面中心）→ 可以退到人物之后。

后层的歌词画在场景画布里，**会被画面转场整个盖掉**。所以
`tools/jizura_plane_audit.mjs` 逐行采样"这一行有多少时间落在转场里"，
超过 35% 的行升到前层——前层在转场之后合成，永远看得见。
落在抽象／全景镜头上的行提层不会压到人脸（实测 11 行的插入镜头占比都 ≈ 0）。

## 四、短行优先可读

JIZURA 把进场和出场压到行长的 92% 以内（引擎 `durs()`），而多数入场动画
还会把字本身淡入——入场没走完之前，字是半透明的，读不出来。
`tools/build_jizura_direction.py` 抄录了引擎真实的进出场时长公式，
逐行（逐分句）算「字真正清晰可见的秒数」：

1. 低于行长 40% → 先只砍入场（保住碎裂／烧尽／雾散这类带语义的出场）；
2. 还是不够 → 进场和出场一起瞬间切。

**短行宁可硬切，也不能让字只剩零点几秒。**

## 五、分句交接不留黑屏

一句里的 `/` 分句，前一句必须清场，但「瞬间切走 + 后一句慢慢淡入」会在屏幕上
留一段没有字的空档。实测 L102 在 206.02 秒只剩 929 个强对比像素。

规则：版式把两个分句放在不同位置时（竖排、分栏、斜带、弧顶、点阵、镜像、螺旋），
让前一句**溶解退场**——交接点两侧总有字，不会黑屏也不会叠成一团；
版式把两个分句叠在同一处（居中、巨字、紧缩、透视）时仍然瞬间切，
否则两句会同时压在画面中央。

可见性审计因此在**每个分句边界前后各取八帧**，并按"连续多少帧完全没有字"量出空档宽度——
换句的换气（几帧）不算丢字，成十分之一秒以上的空洞才算。

## 六、JIZURA 自身不做全屏闪烁

影片的崩坏后期由 `src/signal_windows.mjs` 的授权窗统一闸门控制，
JIZURA 自身的全屏闪烁（`fx.flash`）一律关闭。画面级冲击交给影片的
`applyGlitch`，歌词层只负责阅读层。

引擎的透明后处理会把图层 alpha 自己平方一次，歌词层渲染因此必须传
`{noPost:true}`，否则被强调的行（色散 + 颤抖）整层会被淡掉。

中文译文字幕固定用影片黑 `#090C13` 与纸白 `#E9EDE5`，
不借用日文行的配色——否则翻成墨色行时字幕会变成一条乳白带。

## 七、逐行客观审计

肉眼抽查会被"这一帧刚好在转场里"骗到，所以每一行都用工具量。

**可见性**（`tools/jizura_visibility_audit.mjs`）：把帧渲染两遍——一遍带 JIZURA 日文层，
一遍把引擎的 `drawPlan` 桩掉（中文译文字幕两遍都在，会抵消）——两者的像素差就是日文歌词
在成片里的实际贡献。判定取两个采样点：

- **定型点**：每个分句的入场动画结束之后（字真正被读的时候）；
- **边界点**：每个分句交接点前后各八帧（换句的空档藏在这里）。

**对比度**（`tools/jizura_contrast_audit.mjs`）：在字墨像素上量它与底下画面的 WCAG 对比度，
以及"看不见"的像素比例。

结果（`export/v15m-visibility.json`，改判 L116 之后重跑）：

| 版本 | strong | weak | missing |
| --- | --- | --- | --- |
| 初稿 v15h | 94 | 26 | 6 |
| 定稿 v15l | 116 | 8 | 2 |
| 改判后 v15m | **117** | 8 | 1 |

对比度审计（`export/v15n-contrast.json`）：ok 101 / low 21 / poor 4。
两表合并后的最终判定（`data/jizura_verdict.json`）：
ok 96 / marginal 25 / unreadable 4 / missing 1。

**这 5 行是指标保守，不是真的读不出来。** 对比度审计算的是"字墨像素与它底下
那一像素画面的 WCAG 比值"，逐像素取平均——描边字、抗锯齿边缘、同一行里
明暗混排的字都会被压低。四行 unreadable 加上 L079 一起抽成联系表逐张看过：

| 行 | 判定 | 实看 |
| --- | --- | --- |
| L031 / L126 | unreadable | 白色毛笔字压红天，可读 |
| L066 | unreadable | 红字压在眼部特写上，全片最弱的一行，但它落在影片授权崩坏窗内，是有意的破坏 |
| L102 | unreadable | 深墨竖排压明亮脸孔，可读 |
| L116 | unreadable | 弧顶描边字压纸白房间（改判后已是深墨，肉眼完全可读） |
| L079 | missing | 逐帧扫描证明是采样点伪阳性 |

剩下的两个 missing 用逐帧扫描（`tools/jizura_line_scan.mjs`）逐帧核对过，都是采样点落在
换句空档里的伪阳性：

- **L079**「幸福を手放なす事こそ」：行长的 1.35 秒里有 1.1 秒是 10 万个强对比像素，
  只有开头 0.16 秒是入场遮罩；判它 missing 的那个采样点正好落在两分句之间的 3 帧空档。
- **L100**「編んだ名誉で明日を乞う」：整行都有 7 万–19 万像素，交接处的空档只有
  **6 帧（0.1 秒）**——换句的换气，不是丢字。

修好这三件事之前，L009 在 29.73 秒整行不可见（被转场吞掉）、L102 在 206.02 秒只剩
929 个像素（分句交接黑屏）、117.0 秒那行只有 4.5% 不透明度（继承了调用点的 alpha）。
现在是 L009 在 30.04 秒贡献 248,165 像素，L102 在 206.02 秒的整行都读得出来。

### 采样点会骗人：引擎的 stagger 延迟

引擎给每个分句一个 `stagger`（字符逐个入场的间隔），实际延迟是
`it.delay = mi × stagger`——`mi` 是按歌曲能量算出的"主索引"，高潮段能到 7 左右，
于是分句开头有 **0.15–0.22 秒**字还没进场（`ltI < 0` 时引擎直接 return null，
连底板上的字都不画）。

这带来两个误判：

- **静帧复核采在这个窗口里会以为"这一行没字"。** L070「憐れみにさえ　じきに値がつく」
  的价签版式在 117.49 秒只画出了空价签，看着像整行丢失；
  实际 117.52–118.06 秒字是全的（价签上的粗黑日文完全可读）。
- **审计采样点落在窗口里会把该行判成 weak / missing。**

判据要看**整条时间线**，不是某一帧。`tools/jizura_line_scan.mjs` 逐帧扫描，
`work/trace_text_window.mjs` 直接挂钩引擎的 `J.mainDraw`，把每一帧的
`lt`／`delay`／`ltI` 和"字到底画出来没有"列出来——比猜采样点可靠得多。

## 八、成片与验收

母版：`export/LAST-SIGNAL-1080p60-v15.mp4`——
**1920×1080、60fps、14,553 帧、242.55 秒**、H.264 视频 + 原 AAC 立体声音轨、
312,929,948 字节。

发布版：`export/LAST-SIGNAL-720p30-v15.mp4`——
**1280×720、30fps、7,277 帧、242.57 秒、104,796,181 字节**（3,456 kbps），
由母版隔帧 + Lanczos 缩放重编码，**音轨直接复制、未重新编码**。
抽帧复核：L116 的弧顶深墨字与「数え事が孕んだ熱」的竖排毛笔字在 720p 下依然清晰可读。

```powershell
ffmpeg -v error -y -i export/LAST-SIGNAL-1080p60-v15.mp4 -vf "scale=1280:720:flags=lanczos,fps=30" -c:v libx264 -preset slow -crf 20 -pix_fmt yuv420p -c:a copy -movflags +faststart export/LAST-SIGNAL-720p30-v15.mp4
```

渲染按 24 秒分块、5 路并行，每块独立编码后复制像素拼接，最后合一次原音轨。
L116 改判之后只重渲了受影响的那一块（part-0009，216–240 秒），
其余十块沿用原渲染结果；重新拼接后 10 个接缝仍然逐位一致。

| 校验项 | 结果 |
| --- | --- |
| 帧数 | 14,553 / 14,553（母版）；7,277（发布版，隔帧） |
| 确定性（同帧重复渲染像素一致） | 通过 |
| 首帧保留（分块边界不丢帧） | 通过 |
| 接缝（10 个接缝帧逐位相同） | 通过 |
| 音轨包 | 通过 |
| 闪烁筛查（`tools/check_flash.py`） | 通过，0 个标记窗口 |

最差闪烁窗口是亮度 4 次反向翻转（70.83–71.83 秒）与饱和红 3 次（87.0–88.0 秒），
两处都在影片自己的授权崩坏窗内，属于设计内的破坏，不是歌词层的闪烁。
JIZURA 自身的全屏闪烁始终关闭。

**关于确定性校验工具**：它原本哈希的是 `canvas.toDataURL()` 出来的 PNG 字节，
而浏览器的 PNG 编码器对同一张画面并不保证字节一致（两个页面可以压出不同的字节），
于是报出假的不一致。改成哈希解码后的 RGBA 像素后，三种历史下逐位相同。
实测还发现：影片本体（不含歌词层）在四种历史下完全一致，歌词层的像素也完全一致。

## 九、确定性

- 引擎加载、计划构建、纸纹预热全部发生在装好种子随机数之后，
  每次渲染得到同样的纸纹与同样的随机流；
- 歌词图层不读前一帧、不读系统时钟，全部按歌曲时间求值；
- 同页同 t 重复渲染像素一致（`work/diag_determinism.mjs`）；
- 跨进程与分块边界一致（`tools/jizura_chunk_determinism.mjs`）：
  同一帧在"连续渲染"和"作为某个分块的第一帧"两种历史下必须逐位相同。
