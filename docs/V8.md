# 第八版：颜色让位、人物降级、渲染提速

记录日期：2026-10-24。第八版在第七版（授权时间窗 + 信号式歌词排版）之上做三件事：
**崩坏不再一直抽颜色**、**人物会在高潮里短暂变成线稿/黑白/灰度**、**导出明显更快**。

---

## 一、颜色让位：RGB 分离从"常驻"改成"爆点"

### 问题

第七版里 RGB 分离由 `intensity` 驱动，而 `intensity` 的底噪项 `.72` 永远存在，
所以只要在授权窗口内，分离就一直挂着；黑白（mono）同理，底噪权重 `.40` 让整段画面发灰。
结果是"大部分时间画面其实已经不是原来的颜色了"。

### 做法

颜色类效果全部改挂到打击包络上：

| 参数 | 第七版 | 第八版 |
|---|---|---|
| `split` | `(2 + 20×intensity) × 哈希`，**常驻** | 只在 **4 级打击**且哈希命中 60% 时出现，衰减 `exp(-age×6)` |
| `mono` | `base×0.40 + heavyPulse×0.45`（底噪常驻） | `heavyPulse×0.55`（**只在 3 级以上打击的瞬时**） |
| `noise` | `base×0.45 + heavyPulse×0.5` | `base×0.22 + heavyPulse×0.55` |
| `echo` | `base×0.50 + heavyPulse×0.4` | `base×0.26 + heavyPulse×0.45` |

分离通道也改成**红色主导**：红通道右移满权重，蓝通道左移只留 26% 强度的一丝冷边，
叠加 alpha 从 `.30 + split×0.020` 降到 `.24 + split×0.016`。

### 实测

以 1/60 秒步长扫描全片（`work/glitch_timeline.mjs` → `work/v8-glitch-timeline.json`），
按 `applyGlitch()` 真正生效的阈值 `split > 2.2` 统计：

```
RGB 分离实际时长 1.48 s（全片 0.6%），共 6 段：
  70.60s / 19帧   73.20s / 17帧   87.00s / 14帧
  214.85s / 12帧  219.30s / 9帧   227.00s / 18帧
峰值位移 15.9 – 22.3 px
```

也就是：两个授权窗口里各只有几处鼓点会拉开分离，其余时间画面颜色保持原样。

## 二、人物降级：线稿 / 黑白 / 灰度

### 做法

第八版新增一个"人物降级"通道。授权窗口内的 3 级以上打击上，按哈希抽签：

- 25% 概率触发一次降级，持续 0.42–0.97 秒；
- 样式三选一：`ink`（描线稿）、`mono`（单色版）、`mono` 且 mix 0.62（灰度过渡）。

实现上不新造素材，直接复用项目已有的分级资产
（`assets/character/fx/fx_ink_*`、`fx_mono_*`，由 `config.json` 的 `fxAssets` 映射）。
`src/character_fx.mjs` 的 `drawCharacterFx()` 新增 `resources.fxOverride` 分支：
命中时用 `bodyCanvas()` 以指定分级重绘人物，`mix = 1` 即完全替换。

`src/film.mjs` 在 `renderBaseFrame()` 里求值一次崩坏状态并写入
`resources.glitch` / `resources.fxOverride`；
`src/transitions.mjs` 的转场路径会把这两个值在渲染上一帧后还原回当前帧。

### 实测

```
人物降级实际时长 4.20 s，共 13 次：
  71.92 ink   74.20 灰度  77.17 mono  82.42 mono  88.82 ink   89.32 ink
  189.95 ink  201.30 mono 214.85 ink  215.35 ink  217.65 灰度
  219.30 灰度 224.70 mono 225.20 mono
样式分布：线稿 2.13 s / 单色 1.75 s / 灰度过渡 0.32 s
```

每次持续 0.17–0.65 秒，全部落在两个授权窗口内。

## 三、渲染提速

### 并发上限

`tools/render.mjs` 原来把 `--jobs` 锁死在 2，而本机是 **16 逻辑核 / 10 物理核 / 15.6 GB**。
上限放宽到 8；配合 `--chunk-duration 24`（11 个分段），5 个渲染进程 + 5 个编码进程并行。

### 像素搬运优化

用 `node --cpu-prof` 对 30 帧取样，72.7% 的时间落在 `drawImage`（原生 Canvas 的像素搬运），
按调用链拆分：

| 调用链 | 优化前 | 处理 |
|---|---|---|
| `drawCamera` 相机整帧缩放 | 21.5% | 保留（整体运动不能省） |
| `tint` 人物染色 | 19.3% | 染色画布改为**半分辨率**，像素量减到 1/4 |
| `compositeTransition` 转场合成 | 16.3% | `digital-slices` / `angular-shutter` **只搬运可见的那一条带**，不再整帧贴完再裁 |
| `drawCharacterFx` 人物合成 | 15.6% | 保留 |

### 结果

同一段 30 帧（t = 120.0–120.5）实测：

| | 帧耗时 |
|---|---|
| 第七版 | 145 ms/帧 |
| 第八版（单进程） | **117 ms/帧**（−19%） |

再叠加 5 进程并行，全曲导出从约 25 分钟降到 **约 6–7 分钟**。

## 四、顺带修掉的浏览器端缺陷

`src/glitch.mjs` 里多处 `drawImage` 传的是 2D **上下文**而不是画布元素。
@napi-rs/canvas 容忍这种写法，浏览器的 `CanvasRenderingContext2D.drawImage` 会直接抛
`TypeError`——也就是**预览页只要拖进崩坏窗口就会崩**。
第八版把这些调用全部改成传画布元素（`source` / `scratch` / `split` / `output`）。

改动对原生渲染是像素等价的：改动前后对 11 个崩坏时刻渲染整帧求 SHA-256，
**11/11 完全一致**，因此第七版成片仍然有效、无需重导。
