# 第九版：切点不再空洞、城市重做、黑星染红

记录日期：2026-10-24。第九版在第八版（授权时间窗 + 信号式歌词排版 + 颜色让位）之上做四件事：
**修掉"镜头末尾几帧特效消失"的 bug**、**把城市重做成统一的新风格**、**把黑星改成红与黑**、
**让天空染红、城市被摧毁**，再顺带修掉浏览器端一个确定性缺陷。

---

## 一、修复：每个镜头最后几帧特效没了、画面恢复彩色

### 症状

用户报告：**每个镜头最后几帧画面特效没了，恢复了彩色**。
第八版成片里可以看到，在授权窗口内，每逢场景切换，崩坏效果会短暂"断掉"一小段，
画面突然变干净、颜色回到正常，像是信号在这一瞬间被抹掉了。

### 根因

`src/glitch.mjs` 的 `glitchAt()` 里，崩坏强度由三部分相乘得到：

```
intensity = level × env × cutBoost
```

其中 `env` 是场景的**进出包络**。第八版的包络写法是：

```js
const sceneEnv = smooth(local / .6) * smooth((span - local) / .4);
const env = sceneEnv * smooth((t - window.from) / .4) * smooth((window.to - t) / .4);
```

`smooth((span - local) / .4)` 在**切点前 0.4 秒内**会从 1 平滑降到 0。
也就是说每个镜头临结尾的最后一小段，包络把强度压到 0，崩坏"归零"——
特效全部退场，底噪一去，颜色自然恢复成原样。这不是随机现象，是每场必现的规律性空洞。

同时还有一个连带问题：`level` 直接取**当前场景**的强度，
切点处场景底噪整段跳变（从一个场景的强度瞬间掉到下一个），会叠加成"闪一下"。

### 做法

**1）包络不再归零。** 场景包络只用于控制"切入/切出时的柔和度"，
不再承担"关掉特效"的职责；整体强度保留下限：

```js
const sceneEnv = smooth(local / .45) * smooth((span - local) / .30);
const env = (.62 + .38 * sceneEnv)
  * smooth((t - window.from) / .4) * smooth((window.to - t) / .4);
```

包络最低只降到 **62%**，永远不会归零。切点前后仍保留淡入淡出，
所以观感上"这一场的崩坏比下一场稍弱"的关系没有被破坏。

**2）场景底噪在切点附近交叉淡化。** 新增 `sceneLevelAt()` 与 `mix()`：
切点前 0.30 秒内，底噪从上一场平滑过渡到本场；切点后 0.30 秒内再过渡到下一场。
切点处正好落在两场强度的中间值，不再整段跳变。

**3）切点处反而更烈。** 新增切点增强：

```js
const cutBoost = 1 + .18 * Math.exp(-Math.min(local, span - local) * 7);
```

离切点越近，损坏越强（最多 +18%）。
把"信号在此刻被扯断"读成设计意图，而不是"短暂喘息"。

## 二、城市重做：统一的新风格

### 问题

用户先要求"加强城市的表现效果、当前城市对比度太低"，随后追加"**还有城市场景依然是原来的风格。都按照新风格，增强表现力**"。
原来的城市是好几套互不相关的画法：观测所窗口里是一排平涂小楼，
场景 3/5/9 各自写了一套城市，场景 6 的废墟城市又是另一套。
既不统一，对比度也低（楼体和天空亮度接近，整片发灰）。

### 做法

把城市下沉到 `src/cinema.mjs`，做成两个共用函数，**全片城市共用一套视觉语言**。

**`citySky(c, t, opts)` —— 染色天空**

竖直渐变（顶天 → 天中 → 地平线 → 回顶天），加一层 `lighter` 叠加的地平线辉光。
关键取向是**地平线最亮、越往上越黑**，这样城市楼体天然成为剪影。

**`citySkyline(c, t, color, collapse, opts)` —— 三层剪影**

| 层 | 明度 | 轮廓光 | 窗火 | 视差 |
|---|---|---|---|---|
| 远景 | `alpha(skyLow, .34)` 雾化 | 无 | 无 | 慢 |
| 中景 | `#0A121A` | 50% 强度 | 30% 密度 | 中 |
| 近景 | `#03060A` 近黑 | 95% 强度 | 50% 密度 | 快 |

- 楼体几乎全黑，**只保留朝向画面中心一侧的竖向轮廓光**和顶部一道横边光；
- 窗火按哈希点亮，密度随层级递增；
- `collapse`（崩塌度）驱动三件事：楼体歪斜、整体下沉、**从楼体裂缝里透出红光**；
- 地面废墟剪影 + 上升的火星。

**城市对比度不靠提高楼体亮度，而是靠"亮天空 / 暗楼体"的剪影关系**——
楼体几乎全黑，所以任何一层楼都自带轮廓。

### 统一到新风格的四个位置

| 位置 | 天空 | 天际线 |
|---|---|---|
| 观测所窗口（`architecture()`） | `citySky` + 星场 + 轨道天体 | `citySkyline`，scale .42 |
| 场景 3（FEAR / VASCULAR CURRENT） | 沿用观测所内景 | `citySkyline`，mint 轮廓光 + 窗火 |
| 场景 5（BLACK STAR） | **红透**：`#130509 / #7A1920 / #C33A2E`，rim `#FF8A63` | 被摧毁，`ruin = min(1, progress×.85 + .35)` |
| 场景 6 / `ruinedWorld()` | **红透**：`#150609 / #3C1115 / #8A271E`，halo `#FF6A45` | 远景新式天际线（scale .52），楼体明度差拉大 |
| 场景 9（APPROACH / REALITY） | **红透**：`#120409 / #6B151C / #AE3026`，rim `#FF7A55` | 被摧毁，`ruin .85` |

场景 6 保留 WARNING 的橙色调性（轮廓光用橙色描边），但天空同样染红——
这样"红天"是全片统一的语言，而不是只有某一幕的特效。

## 三、黑星：红与黑

用户指定：**黑星颜色为红色与黑色**，并且**把城市的天空染成红色**、**摧毁城市**。

`src/film.mjs` 的 `blackStar()` 重写为：

1. 外层红色吸积环（保留 `rings()`）；
2. **灼热红色光晕**：径向渐变 + `lighter` 叠加，压在天空与城市之上；
3. **红黑双色碎片拖尾**：54 片碎片，先画黑芯（宽 2.8–5.2）再叠红边（宽 1–2.3），形成硬边双色；
4. **纯黑吸积内核**：径向渐变 `#000000 → #040207 → rim(.30) → rim(.9)`，内缘烧出一圈红；
5. 内核红色裂纹（19 条横向裂痕，裁剪在圆内）；
6. **外缘：粗黑圈（7px）+ 细红环（2.6px）+ 外层淡红环（1px）**。

场景 5 / 8 / 9 与 `worldShot()` 里的黑星全部同步更新：
场景 5、9 用红边黑星 + 红色光晕，场景 8 用黑核 + `#FF5A48` 红色光晕，
场景 6 保留橙色环但内核同样是纯黑。

结果：黑星与被染红的天空形成**硬对比**——
天空是烧红的暖色，黑星内核是绝对的黑，外缘一圈灼红。

## 四、顺带修掉的浏览器端确定性缺陷

### 症状

`--engine browser` 导出在 t = 63.0 / 71.9 报 **"Same-time rendering produced different pixels"**。
同一时刻渲染两次应得到同一张图（这是全片确定性的硬约束），浏览器引擎却做不到。

### 定位

差异集中在**人物区域**（2464 像素），表现为整个角色抗锯齿边缘的亚像素偏移。
`work/browser_cache_probe.mjs` 证明：人物缓存画布的**内容**在同刻两次渲染之间就不同
（hash `8048fa7b` vs `540c17da`）。
`work/browser_wipe_test.mjs` 证明：清空缓存后首帧结果可复现——**冷路径画布与热路径画布存在差异**。

### 三个根因与修法

1. **缓存键不含尺寸**。`canvasFor()` 用同一个 key 复用画布，但画布尺寸随后又被 `canvas.width` 改写。
   改画布尺寸会清空内容，而尺寸变了 key 不变，于是同一 key 的缓存画布被反复重置成不同尺寸。
   修法：**尺寸进键**（`${key}@${width}x${height}`），画布创建后不再改 `canvas.width`，缓存上限 24 项。
2. **`ctx.reset()` 不清空画布**。它只重置状态栈，**不擦除像素**。
   所有复用画布的 `reset()` 必须显式 `clearRect`（`src/character_fx.mjs`、`src/transitions.mjs`）。
3. **导出前冷启动**。浏览器导出在确定性检查前做一次**热身渲染**（`warm(time)`），
   让检查测的是"同一时刻重复渲染是否一致"，而不是"冷启动与热启动是否一致"。
   正式导出时每帧之前都有别的帧，热身让检查条件贴近真实导出。

### 复验

```
node tools/render.mjs --engine browser --start 62.5 --duration 3 --fps 60 --output work/browser-probe-v9c.mp4
```

成功输出 180 帧（1920×1080 / 60fps / 含 AAC），确定性闸门通过；
此前同一段必然失败。

**限制**：浏览器引擎的冷路径画布与热路径仍有亚像素差异（首帧与后续帧不同），
已通过导出前热身规避。**原生引擎（实际出片所用）不受影响。**
